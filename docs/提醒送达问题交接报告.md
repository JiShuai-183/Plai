## 0. 一句话现状

- 线上版本 **2.2.4**，正常工作。
- **一个未解决问题**：日程提醒在「距提醒时刻较远」时**不按时送达**，**要等用户打开 App 才补投**。
- 用户已要求**暂停**此项优化，转去开发其他模块。

## 1. 现象（用户原话 + 实测复现）

**用户报告**：
> 10 分钟后提醒则**准时**；10 小时后提醒则**一直不响，直到打开 App 才响**。

**受控复现（2026-09-13，小米/红米，Android 13+）**：

- 17:44 建 3 条任务，`每日提醒时刻` 分别设为 **18:14 / 19:44 / 21:44**（即 +30 分 / +2 小时 / +4 小时）
- 结果：**只有 18:14 准时送达**；19:44 与 21:44 到点无任何反应
- **打开 App 后，那两条立刻补投出来**

**分界线**：约在 30 分钟 ~ 2 小时之间。这个区间正好是 Android 进入 Doze 的门槛。

## 2. 已确证的事实（**都有实测证据，不要重复验证**）

| # | 事实 | 证据来源 |
|---|---|---|
| 1 | 闹钟**确实注册在系统里**，且**没有被截断** | `dumpsys alarm`：208~210 条，跨 **102 天**（09-14 ~ 12-25），覆盖整学期 |
| 2 | 闹钟是**精确类型**，不是降级后的非精确 | 单条画像：`window=0`、`exactAllowReason=policy_permission`、`flags=0x9`(=STANDALONE\|ALLOW_WHILE_IDLE) |
| 3 | 系统**没有**对它施加 Doze/待机惩罚 | `policyWhenElapsed: device_idle=-- app_standby=-32s952ms battery_saver=-32s952ms` |
| 4 | **电池优化白名单已豁免** | `dumpsys deviceidle whitelist` 含 `user,com.plai.plai,10371` |
| 5 | **MIUI「省电策略」= 无限制** | 用户确认 |
| 6 | **自启动已开** | 用户确认（这是更早一次「划掉后不响」的根因） |
| 7 | **未被后台限制** | `RUN_ANY_IN_BACKGROUND: allow`、`isFrozen=false` |
| 8 | **没有任何被系统移除的记录** | `Removal history` 中 `u0a371` 只有我们自己 `cancelAll()` 的两批（17:23、17:36）；**17:44 建任务之后无任何移除记录** |
| 9 | 闹钟**确实会响** | `Alarm Stats`: `u0a371:com.plai.plai +1s996ms running, 12 wakeups`，最近一次 ≈ 14:05 |
| 10 | **补投是可观测、可复现的** | 2026-09-13 22:45 用 `adb shell am start` 打开 App → 两分钟内**投递计数 12→14**，且已发通知 2000034 / 2000035 **立刻出现** |
| 11 | 通知本身没问题 | 通知记录 `importance=4`（高）、渠道 `plai_task_reminders` 正常、跟随系统默认音 |
| 12 | 2.2.2 及更早的「不响」是**另一个原因** | 那些版本的 release 包**每次提醒投递都会崩溃**（资源压缩误删通知图标，见 §5），2.2.3 已修 |

**由 #10 得出的核心判断**：**闹钟一直在系统里挂着，是系统不在预定时刻投递它；App 一旦变为活跃状态，积压的立刻被补投。**
问题**不在「有没有排上」，而在「排上了却不按时投递」**。

## 3. 已排除的方向（**别再去查这些**）

- ❌ **不是"没排上"或"被 ROM 按数量截断"** —— 208 条、跨 102 天全在（#1）
- ❌ **不是电量优化 / 后台限制** —— 白名单、省电策略、自启动、`RUN_ANY_IN_BACKGROUND` 全部正常（#4~#7）
- ❌ **不是权限或调度降级** —— 精确闹钟授权正常，`window=0`（#2）
- ❌ **不是 App 崩溃** —— crash buffer 干净（2.2.3 之后）
- ❌ **不是我们自己的 `cancelAll()` 误删** —— 建任务之后没有任何取消记录（#8）
- ❌ **不是通知被静默** —— 实测 `importance=4`、渠道正常（#11）
- ❌ **不是"重复发请求就能解决"** —— 见 §6

## 4. 剩余假设与下一步实验

### 假设（按可能性排序）

1. **系统在设备空闲一段时间后延迟投递闹钟，App 变活跃时补投**（Doze 类抑制 / ROM 级策略）。
   与「±30 分成功、2 小时以上失败」的分界线吻合。
2. **闹钟在设备进入 Doze 时被系统"推迟"** —— 即 `dumpsys alarm` 里的 `policyWhenElapsed.device_idle` 被推后。
   目前所有采样都是在设备**活跃时**取的，所以看到的都是 `device_idle=--`。

### 一个可疑但未解释的信号

`dumpsys alarm` 的 **`Allow while idle history`** 段落里**从来没有出现过我们的 app**（只有 3 个其他 app）。
如果我们的 `allowWhileIdle` 闹钟正常在空闲时投递过，应当出现在这里。**这条值得深挖**。

### 下一步实验（明确可执行）

**受控复现 + 连续采样**：

1. 建 3 条任务（`每日提醒时刻` = 现在 +30 分 / +2 小时 / +4 小时）
2. **同时**每 2 分钟采样一次：
   ```
   adb shell dumpsys alarm > dump.txt
   ```
   重点记录每条闹钟的 **`policyWhenElapsed`** 与 **`device_idle`** 字段**随时间的变化**
3. **设备必须真正静止**（不亮屏、不解锁），否则不进 Doze，测不出
4. 对比 `Allow while idle history` 是否出现我们的 app

> ⚠️ **上一次尝试失败的原因（务必避免重蹈）**：架了个每 2 分钟采样的后台监视器，跑了 18 小时共 150 次采样，**但只有 2 次采到了数据**——设备中途断开 adb，其余全是空。**重做时务必保持 USB 连接，并且每次采样后检查是否真的非空**，不要等 18 小时才发现白跑。

## 5. 本轮已交付（背景，避免误判历史现象）

| 版本 | 内容 |
|---|---|
| **2.2.4** | 修 Settings 跳转在 OPPO 等 ROM 上被包可见性误杀（`resolveActivity` 只作用于查询、不作用于启动） |
| **2.2.3** | **紧急修复**：release 包中**每次提醒投递都会崩溃且通知不弹** —— 根因是 Flutter 对 release 应用构建**默认开启资源压缩**，而通知小图标只在 Dart 侧以字符串 `'ic_notification'` 引用，压缩器看不见该引用把它删了 → 插件拿到资源 id 0 → `setSmallIcon(0)` → `NotificationManager.fixNotification` 抛 `Invalid notification (no valid small icon)` → 异常抛在广播接收器内无人接住 → 进程崩溃。修复：`android/app/src/main/res/raw/keep.xml` 用 `tools:keep` 保住该资源 |
| **2.2.2** | 提醒保护页（型号预选 / 一键检测 / 直达系统设置）、通知音跟随系统、通知渠道按「课表 / 日程」拆分、AI 删除日程与课程、AI 密钥只写不读 + 一键粘贴 + 拉取模型、备份脱敏 |

**⚠️ 重要提醒**：**2.2.2 及更早版本的任何「提醒不响」观察，都要先怀疑是上面那个崩溃 bug**，不要直接归因到调度策略。

## 6. ⚠️ 不要做的事（防跑偏）

1. **不要重复验证 §2 里那些已确证的事实** —— 每条都有实测数据。
2. **不要盲目"每次打开 App 重发一遍通知请求"**。
   - 这个逻辑**已经在跑了**：`app_shell.dart` 每次冷启动都调 `rescheduleAll()`，而它开头就是 `cancelAll()` + 全量重排（`notification_scheduler.dart`）。
   - 而且**重发不会让系统更重视它** —— 影响送达的是应用的后台/电量状态与闹钟类型，不是"说了多少遍"。
3. **不要改这些**：渠道划分与渠道 id、通知音策略、`res/raw/keep.xml`、发布脚本的资源闸门、`plai/app_update` 通道。
4. **不要在未证实的情况下上"前台服务常驻"** —— 代价是常驻通知 + 耗电，在根因未明前引入它属于赌博。
5. **真机排查必须记录版本号** —— 否则会把 2.2.2 的崩溃 bug 误判成调度问题（历史上已经这样绕过一次弯）。
6. **不要动已发布的 `releases/*/` 目录**（immutable 缓存一年），要改只能发新版本号。

**排查命令**
```bash
ADB="$LOCALAPPDATA/Android/sdk/platform-tools/adb.exe"
```

## 8. 结论

**问题的定位已经推进到很窄的区间**：不是调度没排上，不是权限，不是电量策略，不是崩溃——**是"闹钟排上了，系统却不在预定时刻投递，直到 App 变活跃才补投"**。

剩下的工作主要在**抓一次设备进入空闲状态时的 `dumpsys alarm` 快照**，看 `policyWhenElapsed.device_idle` 是否被推后。这一步做完，要么定位到系统侧行为（则只能靠保活引导或接受现状），要么暴露我们还不知道的第三种机制。
