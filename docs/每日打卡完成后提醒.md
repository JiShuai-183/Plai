# 每日打卡完成后的提醒修复

## 问题与范围

每日打卡按自然日记录完成，不能用整项任务的 `completed` 标记代替。旧实现打卡后只刷新界面，调度器也未读取打卡日志，导致当天完成后仍收到当天提醒。

本轮针对 Android 修复：保存或撤销打卡后重排该任务；先取消旧通知，再按实际打卡记录寻找下一个未完成的提醒日。取消当天打卡时，尚未到时刻则恢复今天，时刻已过则从未来开始。任务长期或有截止的规则保持，最后一天已完成时取消后不再安排；通知总开关关闭时不重新开启提醒。

日志保存成功与通知更新分开处理：通知失败不回滚打卡，界面仍显示保存结果，并提示提醒更新失败。重新启动 App 的全量重排也读取日志。

## 平台约束

flutter_local_notifications 22.3.0 的 `matchDateTimeComponents: time` 在 Android 和 iOS 都只按时刻匹配，会忽略明确的首个日期；仅把 Dart 首次日期改成明天无法修复。

Android 使用同版本插件已有的原生 Daily 重复协议，保留明确首个日期及后续逐日重复，不增加依赖、通知 ID 或滚动窗口。升级插件时必须复核协议与测试。

同一打卡任务的重排串行执行，防止旧调度的失败降级覆盖新打卡取消结果。存量每日打卡若使用一次性提醒，提醒所属日期已打卡时只取消该次，不顺延为另一条提醒。

iOS 当前公共接口无法同时做到跳过今天及无限重复恢复；本轮不宣称已修复 iOS。在需要跳过自然下一次提醒的情况下取消旧通知并明确报更新失败，后续重排再恢复。未来非连续预打卡日期的离线逐日过滤不在本轮范围。

## 真机验收

自动验证：全库静态检查无问题，完整回归 1074 项通过；包含通知层真实 channel 参数、首触发日期、精确降级、日志失败、同任务并发，以及打卡保存／撤销／离页的回归。Android 真机到时验收已完成，尚未发布正式更新。

使用临时每日打卡，设置几分钟后的提醒：

1. 提前打卡，原定时间不再通知。
2. 提前打卡后退出并重新打开 App，原定时间仍不通知。
3. 原定时间前取消当天打卡，通知恢复；测试后删除临时任务。

长期任务的后续提醒应继续保留。本轮不涉及已暂停的系统省电／Doze 送达延迟问题。

### 2026-11-08 真机实测结果

经用户授权，在 Redmi Android 13 测试机通过界面创建两个临时长期每日打卡，未读取应用数据库或 AI 配置：

- `TestDailySkip_1108`：19:08 提醒前打卡，系统闹钟移至次日 19:08，到时未出现该任务通知。
- `TestDailyRestore_1108`：先打卡，再在 19:09 前取消当天打卡。重启 App 后系统恢复当天 19:09 闹钟；19:09:20 检查到该标题的真实系统通知，并确认已自动注册次日 19:09 提醒。
- 补测重启前跳日：已完成的前一任务改为 19:14，19:12:45 强制结束并重新启动 App；19:13:09 系统只存在次日 19:14 闹钟。19:14:29 检查无该任务通知，次日闹钟仍保留。
- 验收后通过任务详情的二次确认删除两项临时任务；系统中的测试闹钟与通知均已清理。本次只证明次日排程存在，并未等待到次日验证实际送达；iOS 限制不变。
